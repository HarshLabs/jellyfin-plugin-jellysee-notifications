## Determinism rules (every behaviour is a yes/no fact)

1. **Coverage.** A library is *covered* only after a complete, successful, durably committed reconcile pass, and only while the same worker session continues with subscriptions attached and **no dropped callbacks** (`channelDropped == 0`) and no failed/timed-out census since. Worker restart, callback drop, incomplete or failed census, state recovery or a required-call timeout **uncovers** the library until its next complete pass. `CoveredUntil` advances only on a successful complete pass.
2. **Live vs recovery.** An addition is *live* if it was observed by an `ItemAdded` callback **while its library was covered at receipt**, or by a reconcile pass of a covered library whose previous complete pass ended ≤ 30 min before the item was observed. Callbacks received while the library is uncovered (e.g. Jellyfin's own startup scan during recovery) are recovery. The disposition and `FirstSeenAt` are captured when the signal is enqueued and never promoted later. Everything else is *recovery*. Each notice stores an immutable `FirstSeenAt` (never refreshed by audience re-evaluation).
3. **Audible deadline.** An individual add or removal alert is sent only if `now − FirstSeenAt ≤ 30 min` at the moment it is handed to the relay, checked again by the relay before APNs selection for **every** audience (including `sees_all`). Older live work (e.g. relay down for an hour) and all recovery work fold into the summary. Recovered removals are silent.
4. **Summary.** At most **one** summary per server per outage, and **only if the recovery actually found at least one addition** (one Boolean across libraries, not a count); empty or removals-only recovery completes silently. Generic text, **no counts, no titles** ("New items were added to {server} while alerts were paused"), tap opens Recently Added. One compact **presentation key** per server and profile, `r:` + 32 hex chars (hash of server key and profile id), used byte-for-byte as the APNs collapse id **and** the local notification identifier (fits APNs' 64-byte limit; never truncated or re-hashed on the way). Relay pushes, NSE and the app poller therefore replace each other in either arrival order. `outageStart` stays in the payload/state only for the once-per-outage rule. Emitted when recovery completes or 10 min after it started, whichever first; if no addition had been found by the cutoff, the first later qualifying addition may emit the still-unsent summary; after emission, later recovery work in that outage is silent.
5. **Move.** For different IDs, an addition is quiet only if a removal of an item with the same Type and the same non-empty `ProviderDigest` in the same setup is **actually observed** within the move window. Adds whose digest matches an existing indexed title are *held* until that title's removal is observed or the current Jellyfin library scan completes (bounded 30 min); removal observed → both sides quiet; scan ends without removal → it is a real copy/edition → normal alert (subject to rule 3: if the hold made it older than 30 min, it is folded into a summary instead). Adds with no digest or no digest match are never held. The add and removal windows are the same constant.
6. **Health.** Status precedence `restartRequired` > `down` > `degraded` > `healthy`. *Down*: no heartbeat received within the lease (relay clock). *Degraded*: lease valid but any of: loop progress older than 5 min, storage unavailable, a required call stuck, oldest ready outbox work older than 10 min, tooManyUsers, indexFull, uncovered library for > 30 min. *Healthy*: none of those. An idle library needs no recent event acknowledgement. Legacy plugins (no lease field): lease 6 h 30 min, progress unknown.
7. **Webhook.** For a setup whose status is *healthy*, Webhook copies are durably marked silent hints (background refresh only). Otherwise they keep today's visible fallback. Authority is evaluated inside the serialized Durable Object ingestion.
8. **Admin warning.** An outage starts when status leaves *healthy*. After 30 continuous minutes, one warning goes to registrations that report Jellyfin admin (app-reported, labeled as such; the alert carries no sensitive data). One "back to normal" follows only if a warning was sent.

## Security rules (rev 4)

- **S0 Plugin-approved recipient binding.** New private operations (summary, admin health alerts) go only to registrations the plugin has bound. The app calls a plugin endpoint with its relay registration id over its normal Jellyfin session; the plugin derives the user from that session (never from a submitted id), and reports the binding `(registration, profile, user hash)` to the relay over its authenticated setup channel. The relay accepts a binding only from the setup that emits the operation. Unbound registrations get no new private operation; legacy routing is unchanged.
- **S1 Verified admins.** The plugin includes hashed administrator user ids (`Identity.UserHash`, P `Core/Protocol.cs:21`) in each heartbeat. Admin alerts go only to bound registrations (S0) whose bound user hash is in that set. App-reported `is_admin` is never used for delivery.
- **S2 Entitled summaries only.** The plugin records, per outage, the set of hashed users entitled to at least one recovered addition (union of the existing per-notice audiences; a set membership, no counts). The summary goes only to bound registrations (S0) whose user has **current** entitlement to at least one recovered addition, re-evaluated with the existing audience freshness rules at submission and on every retry (no `sees_all` exception, no historical membership). If current entitlement cannot be established, the user is omitted.
- **S4 Suppression authority.** The app's poller stays silent (A1.2) only on the plugin's own runtime health read from **its signed-in Jellyfin server** (authenticated plugin endpoint, any signed-in user, returns `healthy|not` + setup id only), cached ≤ 10 min. Relay health is informational for the app; missing or failed proof keeps fallback alerts. Recovery/quiet hints that advance membership silently are honoured only when they come from that same setup.
- **S5 Bounded health fan-out.** Health deadlines enqueue setup-scoped jobs into the existing durable inbox delivery machinery and share its 100-jobs/20-s alarm budget and fair continuation; no direct whole-roster `deliver()` from a deadline; retired setups' deadlines are removed.
- **S3 Bounded, authenticated health.** Heartbeats stay authenticated by the setup secret. The relay clamps `leaseSeconds` to [600, 1800] for new plugins (legacy implied 6 h 30 min), `progressAge` to [0, 86400], ignores unknown fields, and caps admin-hash sets (≤ 64). Unauthenticated `/status` returns only `health` + `since` (no admin hashes, boot ids, causes or history); diagnostics and the ring are exposed only through the plugin's Jellyfin-admin endpoint (`RequiresElevation`). The diagnostics ring stores fixed cause codes only, never exception messages (they can contain paths).

## Phase R1 — relay (ships first, protects every server immediately, including old plugins)

1. **Heartbeat lease + progress** (R `src/index.ts:600-630`, migration `0005`): store `lease_s`, `progress_age_s`, `boot_id` on `plugin_health`; keep a bounded history (last 50 transitions per setup, new table `plugin_health_events`). Old plugins (no lease) get an implied lease of 6 h + 30 min.
2. **Authority by lease, not ack age**: replace R `src/index.ts:803-806` (`noteSetup` "healthy" = ack ≤ 15 min) with the lease rule. Webhook copies for a healthy setup: never create a visible occurrence; they only nudge a silent background refresh. Unhealthy/no plugin: current Route A behaviour.
3. **No relay heuristic for old plugins** (Astra Q3: no safe threshold). Old plugins keep today's behaviour until they auto-update.
4. **Summary occurrence** (`op: "summary"`, rule 4): sent only to S0-bound registrations meeting S2 that have `CAP_SUMMARY`. Registrations without it get **no recovery push at all** (a silent wake would make an old app's poller replay the backlog); they keep their independent legacy polling, a documented limitation. Rule 3's audible deadline is enforced in `select()` (R `src/index.ts:690-721`) for every audience including `sees_all`.
5. **Admin warning** (S1, S5): sent only to S0-bound admin registrations. One bounded health-deadline map in the existing server Durable Object; its earliest deadline is included in **every** alarm set/delete path (inbox ingestion, quiet scheduling) so no path erases it. It checks lease expiry; sends one localized alert key `pluginDegraded` / `pluginRecovered`.
6. **Status endpoint** (R `src/index.ts:398-416`): public response is `health` + `since` only (S3). The admin row's causes and history come from the plugin's `RequiresElevation` endpoint.

## Phase P1 — plugin 1.1.0 (10.11 → 1.1.0.0, 12 → 1.1.0.1)

1. **Never stay dead** (P `NotificationService.cs:72-154`): `ExecuteAsync` becomes a supervisor that never returns until shutdown. A worker restart requires **proof that the previous worker and all state cleanup completed**, on every exit path including journal constructor and dispose failures (ownership result kept independently of a constructed `Journal`). Proven → log once per hour per cause, back off 1 s…5 min, reopen and replay (never retry an ambiguous transaction in place). Not proven (operation or cleanup still outstanding) → status `restartRequired`, keep heartbeating it, and reopen automatically if the outstanding work later finishes cleanly. Never a second writer.
2. **Library calls off the loop with deadlines** (P `Compat.cs:41-104`, called at `NotificationService.cs:230,245,264,276,296`): two fixed lanes, each one dedicated thread with a bounded request queue: a **census lane** (`Inventory`, `Ids`) and a **live-item lane** (`Get`, `Describe`, `Users`, `Audience`, `GetCollectionFolders`). Per-call deadlines (Ids 120 s, others 15 s). A lane whose call is outstanding is never replaced (no thread pile-up); requests behind it fail fast. Lanes return immutable data; only the processing loop mutates state. Timeout = failed/unknown work: never empty membership, never completed coverage; the library becomes uncovered and status degraded immediately. A loop slice also has an elapsed budget (≤ 2 s of work per iteration). A call stuck > 30 min is reported as `jellyfinStalled` (manual restart is needed only in that case).
3. **Independent heartbeat lane**: a separate timer (not the processing loop) sends heartbeats every 10 min with `leaseSeconds`, `progressAge`, `bootId`, real assembly version, error, outbox depth, oldest pending age. The events sender never parks forever: the `long.MaxValue` sentinel after a non-retryable response (P `NotificationService.cs:319`) becomes a capped re-probe (15 min, honouring relay backoff), reset by a configuration change or a successful probe, so a repaired relay resumes delivery without a Jellyfin restart. One supervisor-owned monotonic limiter counts **all** heartbeat attempts across worker sessions: 6 scheduled per hour, at most 12 per hour in total, honouring relay backoff. The lane reads an immutable snapshot published by the loop (timestamps, cause flags, last-known counters; never fabricated empty counters), never the journal.
4. **Provenance** (P `NotificationService.cs:248-250`, `Engine.cs:26-29`, `Core/Protocol.cs:78-82`): `Notice.Origin = live|recovery` and immutable `FirstSeenAt` (rules 1–3); `CoveredUntil` persisted per library. Recovery adds, over-deadline live adds and recovered removals are never sent individually; the plugin sends one `summary` event per outage (rule 4) and indexes the rest silently. Wire carries `origin` and `firstSeenAt`. **Versioned state migration**: existing notices without provenance are classified `recovery`; old-format files are kept so a downgrade can restore them.
5. **Quiet moves** (rule 5): in `AdvanceAdds` (P `Engine.cs:82-108`) hold digest-matching adds; when the matching removal is observed, commit both sides as quiet (index update, silent hint, no alert). Removal side reuses `Rules.Upgrade` (P `Core/State.cs:206-208`) with the same window constant as the add side. Jellyfin "library scan running" is read from the scheduled-task state (`RefreshMediaLibrary` task).
6. **Diagnostics ring**: `diagnostics.ndjson` in plugin data, 256 KB cap, ring-rotated, one line per state transition / error cause / stall / supervisor restart with UTC + monotonic time; no paths, titles, ids or secrets. Exposed on the plugin config page and in the heartbeat as the last cause code. Written by its own lane; a failure to write it never affects the worker.
8. **Event-driven readiness (latency)**: when an `ItemUpdated` callback (P `NotificationService.cs:191`) arrives for an item with a `pendingAdd` notice, run `AdvanceAdds` for that notice on the next loop iteration instead of waiting for the 30 s `nextReady` tick (`NotificationService.cs:281-287`). The 30 s tick stays as the backstop. Removes up to 30 s from typical alert latency; no rule changes. Sender batching uses a fixed one-second window from the first eligible ready notice per setup (owner decision, 2026-11-03), replacing the sliding 60-second quiet period and five-minute ceiling. Later signals do not extend that window. Per-setup backoff, the shared 20 events-or-bindings calls/minute limiter, processing budget, quiet ordering, binding barriers and 50-event/48-KiB batch bounds still apply. Event attempts use at most ten slots in the rolling minute, reserving the binding lane's existing ten-call allowance within the shared 20-call ceiling. This keeps staggered binding admissions from waiting past their existing 15-second deadline solely because of event traffic. Bindings retain priority; relay backoff and quota remain authoritative. The loop awaits each POST before starting another; burst presentation belongs to the relay.
7. **Runtime status separate from saved config** (P `Plugin.cs:18-25`, `NotificationService.cs:344-348`): stop mirroring live status into the configuration object; the config page reads a runtime status endpoint (admin-only) instead. Fixes the misleading on-disk `Status=notConfigured`.

## Decisions (plugin 1.1.0)

- The companion app repository's `docs/notifications-wire-contract.md` is authoritative. Summaries are one logical outage with one stable event envelope per retained bound profile; the presentation key is derived from the full server key and profile exactly as specified there. Bindings are submitted before dependent events, within the shared events/bindings budget, and are also rotated through heartbeat reports. Every Bind requests a fresh report, including unchanged tuples. Retention is 64 tuples per user/setup and 500 per setup (the relay roster limit), across at most twenty active/retained setups. Only the requesting user's own oldest approval can be evicted; cross-user replacement and an exhausted shared quota with no own approval are rejected.
- 1.1 state lives only in the plugin data directory's `v6/` child (name retained to minimize churn); unreleased v4/v5 layouts are not imported. Import copies and validates only the released 1.0.1 root snapshot/journal, classifies legacy notice provenance as recovery, publishes a complete snapshot and migration marker, and leaves the original files untouched. Downgrade reads the originals; re-upgrade resumes v6. Recovered item identities are retained locally to establish current summary entitlement; no media metadata or counts are added to summary payloads.
- Two process-lifetime library threads return detached snapshots through bounded polling queues. Pending requests yield the processing slice; a timed-out thread keeps its slot until it actually returns. The state ownership token exists independently of Journal construction, and only successful final cleanup permits a new writer.
- Callback signals capture an immutable set of covered libraries at receipt. Each eligible callback is admitted as durable pending-add work before any metadata read. Shared, bounded coverage proofs and the original event identity/time survive removal and restart; `AdvanceAdds` performs metadata evaluation. A detached inventory also publishes roots for pure in-memory receipt-time path matching; those paths are never persisted or exposed. Unknown or uncovered roots fix the signal as recovery before any delayed metadata read. Resolving folders later can only retain or reduce that authority, using the captured coverage set. A coverage epoch fences callback drops and incomplete scans against a concurrent successful-pass commit.
- Indexed IDs remain quiet without a time limit; removed IDs stay quiet within 24 hours of their tombstone, regardless of provider metadata. Cancel held same-route removals after re-indexing, preserving quiet hints for departed routes. Resume any original unacknowledged live add using its original event ID and discovery time. Different IDs remain eligible normally; a removed ID re-added after 24 hours may alert again.
- A matching indexed digest holds an add until the running scan ends (maximum 30 minutes). With no running scan, it waits the existing symmetric ten-minute move window. Only an observed matching removal silences it; an unremoved edition alerts after the hold, subject to the audible deadline.
- Scheduling, heartbeat limits, health ages, retry waits and processing budgets use monotonic time. Protocol observation/evaluation times advance from a UTC/monotonic anchor which rebases after a detected clock correction. A durable sequence fence makes all pre-correction individual work quiet across replay; first-seen/origin values remain immutable. The pending correction survives an ambiguous commit until a clean reopen verifies its marker, and the recovery cutoff shifts without changing outage identity. A detected wall-clock step over 120 seconds invalidates coverage and folds pending audible additions into recovery; immutable observation timestamps are preserved.
- Diagnostics use a dedicated writer and a bounded last-1,024-entry NDJSON ring (under 256 KiB), persisted in `diagnostics/diagnostics.ndjson` below plugin data. Only fixed contract cause codes enter it; failed diagnostic I/O cannot fail the notification worker. Runtime health/counters are separate from saved configuration.
- The automated soak uses a virtual monotonic clock for a deterministic thirty-minute fault timeline. No live Jellyfin or relay service is involved. The existing CI OS/architecture matrix remains intact.
